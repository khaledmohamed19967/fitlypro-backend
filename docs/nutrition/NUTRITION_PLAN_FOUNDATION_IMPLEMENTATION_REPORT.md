## Embedded Tree

```
NutritionPlan
  └── nutritionDays[]     (NutritionDay, _id)
        └── meals[]       (Meal, _id)
              └── foodItems[]  (PlanFoodItem, _id)
```

Each embedded level has its own `_id` for stable frontend references and future edit/swap/logging flows.

### NutritionDay

- `dayNumber` (1–14, unique per plan)
- `name` (optional; helper generates `Day N` when omitted)
- `notes` (max 500)
- `meals[]` (may be empty — valid draft/rest day)

No `dayOfWeek` — `dayNumber` only.

### Meal

- `order` (1-based, unique per day)
- `name` (required, max 120)
- `mealType` (optional enum)
- `suggestedTime` (optional HH:mm)
- `notes` (max 500)
- `foodItems[]` (max 30; empty allowed in draft)

### PlanFoodItem

- `foodId` (ObjectId → Food)
- `order` (1-based, unique per meal)
- `quantity` (> 0)
- `unit` (g, kg, ml, l, piece, serving)
- `notes` (max 200)
- `foodSnapshot` (server-generated via `buildFoodSnapshot`)

Same `foodId` may appear multiple times across meals — only order uniqueness is enforced per meal.

## Ownership

Mirrors WorkoutPlan and Food modules:

| Kind | ownership.type | ownership.trainerId | trainerId |
|------|----------------|---------------------|-----------|
| System | `system` | null | null |
| Trainer | `trainer` | owner id | owner id |

Pre-validate hook keeps `ownership` and `trainerId` synchronized. Trainer plans cannot have `templateKey`.

Helpers: `resolvePlanOwnership`, `buildNutritionPlanVisibilityFilter`, `canReadNutritionPlan`, `canModifyNutritionPlan`.

---

## Validation

Joi schemas in `nutrition-plan.validator.js`:

- `validateCreateNutritionPlan` — required plan metadata + optional nested tree
- `validateUpdateNutritionPlan` — partial update; `nutritionDays` when present is authoritative full replace (Phase 4)
- `validateNutritionPlanQuery` — prepared for Phase 4 list endpoint

**Forbidden in request bodies:** `trainerId`, `ownership`, `templateKey`, `clientId`, `startDate`, `endDate`, timestamps, denormalized counters, computed macro fields, client-supplied `foodSnapshot`.

**Macro targets:** calories > 0; protein/carbs/fat >= 0. No percentages stored.

Mongoose pre-validate enforces unique `dayNumber`, meal `order`, and food item `order` within their scopes.

---

## Normalization

Helpers sort and renumber the full tree before persistence:

| Level | Sort by | Renumber to |
|-------|---------|-------------|
| Days | `dayNumber` | 1..N |
| Meals | `order` | 1..N |
| Food items | `order` | 1..N |

Existing valid `_id` values are preserved; missing IDs are generated by Mongoose on save.

`normalizeNutritionPlanInput` trims strings and applies full tree normalization.

---

## Food References

Plan food items store **`foodId` + `foodSnapshot`**, not a full embedded Food document.

Snapshot is built with the Phase 2 helper:

```js
buildFoodSnapshot(food) // from food.helpers.js
```

Snapshot shape: `{ name, brand, category, nutritionPer100g, defaultServing }`.

`processNutritionDaysFoodItems` loads visible foods, attaches snapshots, and validates units.

---

## Snapshot Strategy

- Client sends `foodId`, `quantity`, `unit`, `order`, optional `notes`
- Server loads Food via `buildFoodVisibilityFilter(trainerId)`
- Server generates snapshot at write time (Phase 4 service will call this)
- Foreign trainer foods are rejected (not visible)

## Macro Calculations

Pure functions in `nutrition-plan.calculations.js` — nothing persisted:

| Function | Purpose |
|----------|---------|
| `convertQuantityToGrams` | Unit → grams (1ml ≈ 1g MVP) |
| `validatePlanFoodItemUnit` | Unit + gramWeight rules |
| `calculateItemMacros` | nutritionPer100g × (grams / 100) |
| `calculateFoodItemMacros` | Item with snapshot |
| `calculateMealTotals` | Σ item macros |
| `calculateDailyTotals` | Σ meal totals |
| `calculatePlanComputedMacros` | Average daily macros across days |

Denormalized plan fields via `applyPlanDenormalizedCounters`: `totalMeals`, `totalFoodItems`, `avgDailyCalories`.

## Known Limitations

- No CRUD endpoints or service layer yet

- No client assignments or scheduling
- Liquid density not modeled (1ml = 1g convention)
- Macro rounding for API responses deferred to Phase 4
- `validateNutritionPlanQuery` defined but not wired to middleware
- Denormalized counters applied via helper; Phase 4 service will call before save
